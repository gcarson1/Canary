# Architecture: Modular Expansion Patterns

The 4-thread topology is the foundational standard used by modern commercial DAWs (like Reaper, Bitwig, and Ableton Live), and it provides a solid base for modularity. However, to prevent the codebase from turning into a tangled monolith as it scales from a basic 4-track player to a full production environment (supporting complex routing, sidechaining, multi-core DSP, and unstable third-party plugins), the design needs **five specific modular expansion patterns** right now.

---

## 1. Shifting from a "Track List" to a Directed Acyclic Graph (DAG)

In Phase 2, starting with a flat `Vec<Track>` that sums into a Master Bus is fine, but it breaks down the moment you want **aux sends/returns, group buses, sidechain compression, or folder tracks**.

* **The Modular Solution:** Represent *everything*—tracks, buses, plugins, hardware inputs, and master outputs—as a uniform trait: `AudioNode`.
* **How it scales:** The audio engine doesn't care what a node does; it only traverses a compiled **execution schedule** (a topologically sorted flat array of node IDs and buffer indices).
* **Lock-Free Graph Swapping:** Nodes live in a persistent `NodeArena` (`MAX_NODES` = 4096 slots, indexed by `NodeId`) owned by the **Audio Thread**, so node state (smoothers, later delay lines and plugins) survives graph edits. An `ExecutionPlan` holds the schedule plus all its pre-allocated scratch buffers, and the node changes to make when it goes live:
    * **Schedule:** steps by `NodeId`, acyclic by construction (a step may only read from earlier steps; the last step is the master output).
    * **Node changes:** `insert`, `remove`, and `update` (new data swapped into a live node in place via `AudioNode::exchange`; the old data stays in the plan).
    * **Main Thread:** `LiveNodes` mirrors the arena. `EngineHandle::send_plan` validates the plan against it, then queues the `Box<ExecutionPlan>` through the `rtrb` command queue.
    * **Audio Thread:** at the top of a block, and only if the garbage queue has room, it calls `NodeArena::apply` (removals, inserts, updates), moves removed nodes into the retiring plan, and pushes the old plan to the garbage queue. `EngineHandle::collect_garbage` frees it on the Main Thread. Nothing is allocated or dropped on the Audio Thread.

```rust
pub trait AudioNode: Send {
    fn process(
        &mut self,
        inputs: &[&[f32]],
        outputs: &mut [&mut [f32]],
        midi_in: &[MidiEvent],
        midi_out: &mut Vec<MidiEvent>, // Pre-allocated capacity!
        context: &ProcessContext,
    );
    fn latency_samples(&self) -> u32 { 0 }
    fn reset(&mut self);
    fn exchange(&mut self, _data: &mut (dyn Any + Send)) {} // Audio thread: no alloc, no drop
}
```

Live MIDI reaches only steps marked with `ExecutionPlan::route_midi`; every other node gets an empty `midi_in`. The app marks only the selected track's instrument, so the first MIDI input and the sampler pads (which share one `MidiSender` behind a mutex, never locked on the audio thread) play that track. `TrackNode` sums its inputs before gain/pan, so an instrument node feeds a track through its inputs.

### Sequenced MIDI, Automation, Taps and the Metronome

* **Sequenced notes:** `ExecutionPlan::sequence(step, events)` gives a step `SeqEvent`s (timeline samples, sorted; note-offs before note-ons at the same sample) that play with the transport, merged in time order with live MIDI. Per-step `NoteState` (`daw-graph/src/sequence.rs`) tracks held notes and the expected next playhead; on stop, seek, loop wrap or a changed sequence it emits note-offs at offset 0. Output never grows past `midi_out`'s capacity. On a plan swap `adopt_notes` carries each step's state to the same node in the new plan: notes play on if the sequence is unchanged, else they are released.
* **Loop and block splitting:** `Command::SetLoop(Some((start, end)))` (ignored unless `start < end`). The engine renders a block in chunks of at most `max_block` frames and no further than `Transport::frames_until_wrap`, so a wrap always falls between chunks.
* **Count-in and metronome:** `Command::CountIn { frames, beat, beats_per_bar }` (ignored while playing) holds the playhead while it clicks; the plan's clicks (`ExecutionPlan::set_clicks`, timeline samples, `data[0] == 1` on downbeats) sound while the transport rolls with `Command::SetMetronome` on. `daw_dsp::Click` is mixed into the output after metering, so meters never see it.
* **Device streams:** `start_output_at(capacity, rate, faults)` asks the default output for a saved project's rate when the device offers it in f32 (`stream::pick_config`), else takes the device's own config; `start_input` asks the input for the output's rate the same way. A mono device hears (L+R)/2. Stream error callbacks only set bits in `StreamFaults` (cpal reports xruns on the render thread); the app shows them each frame, and a lost device ends any take. Rebuilding the stream on a new device is not built: the app asks for a restart. Takes stop cleanly at the WAV format's 4 GiB limit.
* **Automation:** `AudioNode::automate(id, value)` sets a node's own parameter id (`TrackNode::GAIN`/`PAN`, a plugin's param ids). `ExecutionPlan::automate(step, id, points)` takes `AutoPoint`s (samples, with a curve) and, before every block, playing or not, applies `daw_core::automation_value` at the playhead, so a seek lands on the automated value.
* **Taps:** `ExecutionPlan::tap(step, Box<dyn Tap>)` hands a step's first two outputs to `Tap::write` after each block (audio thread: no alloc, no lock). `daw_graph::PeakTap` feeds a track's meter after its effects. `daw_engine::bounce_tap(input, max_block, end)` writes a step to a recorder only while the transport rolls and only up to sample `end`; for export the app calls `compensate`, reads `step_latency(step)` and taps up to `end + skip`, then trims `skip` samples off the file's front, so plugin delay does not shift the render.

### Routing

* **Ids:** tracks have stable `Track::id`s; outputs, sends and sidechains point at ids, and `Project::new_track_id` never reuses one still referenced. Only buses (`Track::bus`) can be targets; a bad or non-bus output goes to the master. A send (`routing::Send`, linear level 0..=2) is post-fader and becomes a `daw_graph::SendNode` (level atomic, 20 ms glide).
* **Order:** `Project::route_order` sorts tracks so every source (output, send or sidechain) precedes what it feeds, or returns `None` on a cycle (the app then falls back to track order). `Project::solo_set` keeps the soloed tracks plus every bus they feed and every source of a soloed bus.
* **Sidechain:** `EffectNode` inputs 2-3, when wired, are the key (`process_keyed`); the app wires them to the source track's last step.
* **Node ids in `canary`:** master 0; tracks `1..=1023` (`MAX_TRACKS`, id = index + 1); sends `1024..=2045`; `PREVIEW_NODE` 2046; `REFERENCE_NODE` 2047; plugin and built-in devices from 2048 (`devices::FIRST_DEVICE_NODE`). `PreviewNode` (the browser's one-shot sample voice, fed through `Preview`'s rtrb queues) joins the mix but not an export's.

### Buffer Contract

Scratch buffers are allocated to `max_block_size` and reused across the schedule, so they always hold stale audio.

* **Compiler/Executor:** slices every input and output to exactly `context.num_samples` frames before `process()`, pre-zeroes summing buses and any buffer passed to an untrusted third-party plugin, and matches channel layouts (mono into stereo passes the same buffer twice, or inserts an adapter node).
* **Node:** every output channel it does not actively write is filled with `0.0`.

## 2. Out-of-Process Plugin Sandboxing (Crucial for macOS)

Third-party AU and VST3/CLAP plugins are the #1 cause of DAW crashes. Furthermore, on Apple Silicon Macs, users frequently run older `x86_64` plugins inside an `arm64` native DAW.

* **The Modular Solution:** Design `PluginNode` so it can operate either **In-Process** (direct function pointer call) or **Out-of-Process** (via macOS XPC / POSIX shared memory `shm_open` + Mach semaphores).
* **Future Growth:** By abstracting plugin hosting behind the `AudioNode` trait now, you can start by running plugins in-process and later move them into separate worker processes (like Bitwig's sandboxing) without touching a single line of the core Audio Engine or UI code. If a buggy synth segfaults, only the child process dies, and the DAW stays open.
* **In-Process Split (CLAP, `daw-host`):** `ClapPlugin` is not `Send` and stays on the Main Thread (params, state, callbacks). Its `PluginNode` runs in the arena and gets pre-zeroed buffers. The node is dropped on the Main Thread through garbage collection, so it must be removed from the graph and collected before its `ClapPlugin` is dropped, or the plugin leaks.
* **Formats (`daw-host`):** CLAP (`clack`), Audio Units (AU v2 via `objc2-audio-toolbox`) and VST3 (`vst3` crate) each pair a main-thread handle with an `AudioNode`. `daw_host::Catalog` scans all three and instantiates any of them behind the `Hosted` trait. CLAP plugins may have up to 8 audio ports per direction: the node's inputs feed the main port (0), other input ports (e.g. sidechain) get silence, and only the main output port is heard. VST3 plugins with more than one audio bus per direction are rejected for now.
* **Bundled plugins:** Canary ships three GPL-3.0 instruments as unmodified CLAP builds: Surge XT 1.3.4 (plus Surge XT Effects), Dexed 1.1.0 and OB-Xf 1.0.3. `scripts/fetch_plugins.sh` downloads pinned, checksummed releases into `third_party/plugins/` (gitignored) and installs factory data in `~/Library/Application Support` if missing; `scripts/bundle.sh` copies them into `Canary.app/Contents/PlugIns` (signing unsigned ones). `Catalog::scan` looks in `Contents/PlugIns` (or `third_party/plugins` for a `target/<profile>` build) first, marks those entries `bundled` (the picker tags them `STOCK`), skips user-installed copies with the same id, and falls back to the bundled copy when a saved bundle path is gone.
* **Built-in effects (`Format::Builtin`):** compressor, saturator, dynamic EQ (bell or threshold-triggered low cut) and de-esser are pure DSP in `daw_dsp::effects`; EQ, reverb, delay (SYNC to note lengths at the song tempo), true-peak lookahead limiter (1.5 ms lookahead plus 6 samples of detector lag, 78 samples at 48 kHz), gate, filter, chorus/flanger, phaser, bitcrusher and utility are in `daw_dsp::fx`, all built by `effects::effect(id, sample_rate)` (ids `canary.*`). `canary.eq8` (8-band parametric EQ) writes its output to a `daw_dsp::Scope` (lock-free ring; the UI reads an FFT spectrum) and the rack draws its curve (`eq8_response_db`) over the analyzer. `canary.pitch` and `canary.tune` (`daw_dsp::pitch`) are time-domain: two triangle-crossfaded read heads slide through a delay line at the pitch ratio, centred on a fixed delay of half the longest grain plus 4 samples (reported as latency: about 50 ms for `canary.pitch`, 15 ms for `canary.tune`); with no shift one head eases to full gain at that delay, so nothing combs; the tuner detects pitch with YIN on the mid signal at half rate every 512 samples and glides the shift toward the nearest scale note at SPEED. `daw_dsp::airwindows` ports ToTape6, Density2 and PurestDrive (MIT) in f64, without their dither or dry/wet (the node's MIX does that). `canary.amp` (`daw_dsp::nam`) runs Neural Amp Modeler WaveNet captures (standard/lite/feather/nano; not LSTM, gated, bottleneck or A2 models yet) sample by sample on the mid signal, with fixed-width layer kernels for 16/8/4/2 channels (about 15% of a core for a standard model at 48 kHz). Effects that load a file hand out a `FileLoader` (`Effect::file_loader`) when made: the built-in handle parses on the main thread, sends the model over rtrb, gets the old one back to drop, and saves the path as a `FILE=` state line; `Hosted::file`/`load_file` expose it, and dropping a `.nam` from 01 on the module sends `Request::LoadSample`. `canary.cloudseed` (`daw_dsp::cloudseed`) is a sample-by-sample Rust port of CloudSeedCore (MIT): twelve modulated delay lines per side with diffusers, a shelf and a low-pass in each loop; buffers are sized at the sample rate, seeds made once. `canary.convolver` (`daw_dsp::convolve`) convolves with a synthesized stereo impulse response (filtered decaying noise) through `fft_convolver::TwoStageFFTConvolver`; building one allocates, so each instance has a worker thread that rebuilds it when DECAY or DAMP change and hands it over an rtrb queue; the replaced engine is fed silence until its tail rings out, then goes back to the worker to be dropped. The `Effect` trait also has `latency()` (fixed once the sample rate is set), `set_tempo(bpm)` (called before each block from `ProcessContext::musical`) and `scope()`. `daw_graph::EffectNode` wraps any of them, delays its dry signal by the effect's latency so MIX/MATCH/DELTA line up, reports it as `latency_samples()` (the built-in `Hosted` handle reports the same for PDC), and adds MIX (dry/wet), MATCH (automatic level matching for A/B, off by default: the wet signal is held at the dry signal's loudness over a 1 s window, within ±24 dB, frozen below -70 dBFS) and DELTA (output wet minus dry). MIX, MATCH and DELTA have fixed parameter ids from `daw_core::COMMON_PARAM_ID` (1000), so automation stays on them when an effect gains parameters; `.daw` format 1 files are migrated on load. Parameters are atomics shared with the main thread; level knobs glide over 20 ms; non-finite input is zeroed. State saves as `NAME=value` lines. Racks reorder by dragging a module's title (`Action::MoveDevice`).
* **Synth (`canary.synth`, an instrument):** `daw_graph::PolySynthNode`: 16 voices, two band-limited oscillators, a resonant low-pass with its own envelope, amp ADSR and glide. Its params live in a `ParamBank` (`SYNTH_PARAMS`) shared with the main thread. It plays sequenced and live MIDI.
* **Sampler (`canary.sampler`, an instrument):** `daw_graph::SamplerNode` plays `Zone`s (a sample region, key and velocity range, root key, round-robin cell, one-shot flag) with 32 voices, cubic interpolation, attack/release and a retrigger choke. The main-thread `daw_host::Sampler` owns the layers (files by key zone and velocity zone; layers in the same cell take turns) and slicing (`daw_dsp::slice`: transients, grid, manual markers, snapped to zero crossings). It rebuilds the zone list on any shaping change and sends it over an rtrb queue; the node swaps it in at block start and sends the old list back to be dropped. MODE 2 maps slice *n* to key ROOT + *n* (the pads). The app loads layer files with the same loader as clips and hands the audio over (`Devices::feed_samplers`). State: param lines, `LAYER=key,velocity,path`, `MARKER=fraction`.
* **Master and metering (`daw_graph::MasterNode`, node 0):** inserted once and never rebuilt, so meters keep their history. It meters the mix only: BS.1770-4 loudness (`daw_dsp::Loudness`: K-weighting at any rate, momentary 400 ms, short-term 3 s, integrated with absolute and relative gates over a fixed histogram), 4x oversampled true peak (`daw_dsp::TruePeak`, hold until reset) and correlation. Readings and controls go through the shared `Monitor` atomics. It outputs stereo, mid or side, and A/B-switches (10 ms crossfade) to the project's reference track, a `TrackNode` at node 2047 feeding the master's inputs 2-3. The reference is gain-matched by its offline integrated loudness against the mix's integrated (else short-term) loudness, within ±24 dB. Delta monitoring is per effect (DELTA).
* **Plugin editors:** `Hosted::open_editor(parent NSView)` embeds the plugin's own UI: AU via its Cocoa view bundle, else CoreAudioKit's `AUGenericView`; VST3 via `IPlugView` (`kPlatformTypeNSView`); CLAP via the `gui` extension (embedded Cocoa, host `gui` extension for resize requests). daw-host only passes raw view pointers; the AppKit window lives in the `canary` app (`editor.rs`): a layer-backed content view, so Core Animation composites it on Metal. Editors close before their plugin is retired or dropped. `cargo run -p canary --example editor_check` opens every Apple AU's editor offscreen.
* **ARA 2 (`daw_host::ara`):** Celemony's ARA_API 2.3 headers are vendored in `third_party/ARA_API` (Apache-2.0); `ara/sys_aarch64.rs` and `sys_x86_64.rs` are bindgen output checked in (struct packing differs per CPU), so builds need no libclang. `Hosted::ara_factory` finds a plug-in's factory (AU `AraF` property, VST3 `ARA::IPlugInEntryPoint` on the component, CLAP `org.ara-audio.ara.pluginextension/2`). `ara::Document` (one per factory) owns the document controller and implements the host's audio access (reads `SampleData` as f32/f64, zero outside the file) and archiving controllers; content access, model updates and playback requests are omitted. `Catalog::instantiate_ara` binds a new instance (playback renderer + editor view roles) before setup, as ARA requires. ARA only lets a renderer's regions change while the plug-in is inactive, so `instantiate_ara`'s `on_bind` callback hands the instance its track's regions before activation and they stay fixed: moved or trimmed clips update their region in place (allowed while rendering), but when a track gains or loses regions `Document::sync` reports it and `Devices::sync_ara` retires that track's ARA instances, which the next sync makes again (state kept). A removed region lives on until no retired instance renders it (`Document::release`). In the app the track node stops playing an ARA track's clips. Call order is tested against a fake plug-in; untested against a real ARA plug-in (none installed). Document archives (`Document::store`/`restore`) are saved in the project's `ara` list per factory id; the app restores one once none of its clips is still loading (sources and modifications carry path-based persistent ids, so the plug-in matches its edits to the right audio), and on save writes back unrestored or unreadable archives unchanged rather than overwrite them.
* **In the app:** plugin nodes persist across plan rebuilds (ids from 2048 up). A removed plugin's handle is dropped only after its node has left the engine.

## 3. Transitioning from Single-Core to Multi-Core DSP

Initially, the CoreAudio callback runs on a single high-priority thread. Once a user loads 50 tracks with heavy reverb and virtual instruments, a single CPU core will bottleneck even when the other 9 cores on an M-series chip are idle.

* **Why the DAG matters here:** Because the engine is a Directed Acyclic Graph (DAG), independent branches of the graph (e.g., Track 1 through Track 32 before they hit the Master Bus) have zero data dependencies on each other during a single buffer tick.
* **The Upgrade Path:** Later on, you can replace the single-threaded topological loop inside the Audio Engine with a real-time work-stealing thread pool (anchored by Mach real-time thread policies and atomic dependency counters) without rewriting any DSP nodes, UI, or disk streaming code.

## 4. Automatic Plugin Delay Compensation (PDC)

Lookahead limiters or linear-phase EQs introduce a fixed sample delay (e.g., 512 samples). Without modularity for this, tracks with plugins will play out of phase with dry tracks.

* **Building it into the trait now:** By including `fn latency_samples(&self) -> u32` on the `AudioNode` trait from day one, the graph compiler on the Main Thread can walk the DAG, calculate the maximum latency path, and automatically insert hidden delay ring buffers onto parallel paths with lower latency.
* **Built (`ExecutionPlan::compensate`):** `EngineHandle::send_plan` runs it on every plan. Each step's inputs arrive when its slowest source is ready; every faster source edge gets a ring buffer of the difference, and a step's output is ready that much plus its node's latency. Nodes inserted by the plan report their own `latency_samples()`; nodes live from an earlier plan (persistent plugins) need `ExecutionPlan::set_latency`. Latencies clamp at `MAX_LATENCY` (2^20 samples). On a plan swap `adopt_delays` hands each edge's in-flight audio to the new plan when the edge (step node, input, source node, channel) and its delay are unchanged, so edits during playback do not drop audio (track node ids are positional, so inserting or removing a track while playing re-keys the tracks after it, and their in-flight audio restarts). `ExecutionPlan::latency()` is the master's total lag; `EngineHandle::plan_latency` exposes it and recorded audio takes are moved earlier by it; the engine clicks the metronome and stamps the live MIDI log at the timeline position being heard (the transport minus it), so MIDI takes line up the same way. Live MIDI input is not compensated, so instrument steps report 0. Built-in effect latency is fixed per sample rate; AU and VST3 latency is read live, and the app rebuilds the plan when an effect's latency changes.

## 5. Recommended Cargo Workspace Layout for Long-Term Modularity

To enforce strict boundaries at compile time (so a UI developer or contributor can never accidentally import a blocking mutex into the DSP crate), structure the Rust workspace into decoupled crates:

| Crate Name | Responsibilities | Allowed Dependencies |
| --- | --- | --- |
| **`daw-core`** | Pure data types: `Sample`, `TimeSignature`, `MidiEvent`, `NodeId`, `ParameterId`, Command/Telemetry enums. | Zero heavy dependencies (`no_std` compatible if desired). |
| **`daw-dsp`** | Pure signal processing primitives (biquad filters, envelopes, oscillators, delay lines, FFT), the built-in effects, the metronome `Click`, and offline `stretch` (WSOLA time-stretch and pitch-shift, run on a worker thread). | `daw-core`, `fft-convolver` (convolution), `rtrb` (hand-offs to the audio thread), `serde`/`serde_json` (reading `.nam` captures). **Zero OS or UI dependencies.** |
| **`daw-graph`** | The `AudioNode` trait, topological sorter, PDC calculator, and `ExecutionPlan` compiler, and the built-in nodes (tracks, sends, effects, synth, sampler, preview, master). | `daw-core`, `daw-dsp`, `rtrb`. |
| **`daw-engine`** | Real-time thread coordinator, `cpal`/`coreaudio-rs` stream management, `rtrb` queues, disk streamer, and garbage collector. | `daw-core`, `daw-dsp` (`.pek` waveform cache, `Click`), `daw-graph`, `rtrb`, `symphonia`, `rubato`, `hound`, `midir`. |
| **`daw-host`** | CLAP (`clack`), VST3, and AudioUnit wrappers that implement `AudioNode`; Canary's built-in effects behind the same `Hosted` handle. | `daw-core`, `daw-dsp`, `daw-graph`, `clack-host`/`clack-extensions`, `vst3`, `libloading`, `rtrb`; macOS: `objc2`, `objc2-audio-toolbox`, `objc2-core-audio-types`, `objc2-core-foundation`. |
| **`daw-project`** | Undo/Redo command pattern (`Action` trait), serialization (`serde`), `.daw` project file bundles, and state management. Stores track devices (plugin format, bundle, id, base64 state). Also: notes, patterns and pattern clips in ticks (`PPQ` = 960; `Project::sequence` turns them into `SeqEvent`s); tempo and meter maps (`samples_at`/`ticks_at`, bars and beats); `smf` (read formats 0/1, write format 0); `edit` (quantize, transpose, shift, duplicate, legato, velocity, humanize, each returning notes for `Action::SetNotes`); automation lanes (`Target::Gain`/`Pan`/`Param`, `Project::envelope`); routing (see section 1); clip `gain`, `reverse` and `Stretch` (the original file, ratio, semitones). `History::apply_gesture` folds a drag into one undo step; `History::save_copy` writes without marking saved (autosave, template). | `daw-core`, `serde`, `serde_json` (`.daw` files). |
| **`daw-ui`** | macOS windowing, timeline canvas, mixer views, and user input translation into `daw-project` actions. | `daw-core`, `daw-dsp` (pure data only: `WaveformPyramid`/`MinMax`), `daw-project`, `egui` (custom-painted). |
| **`canary`** | The `eframe` app binary: wires `daw-ui`, `daw-engine` and `daw-project`; builds engine plans from the project, loads audio on worker threads, records takes, saves; hosts plugin editor windows. | `daw-core`, `daw-dsp`, `daw-graph`, `daw-engine`, `daw-host`, `daw-project`, `daw-ui`, `eframe`, `egui`, `cpal`, `hound`; macOS: `objc2`, `objc2-app-kit`, `objc2-foundation`. |

### Why this workspace structure pays off

1. **Headless Testing & CI:** Because `daw-graph` and `daw-engine` don't depend on `daw-ui` or even a physical soundcard when running an offline buffer loop, you can run automated unit tests and benchmarks (`cargo bench`) on the entire mixing engine in GitHub Actions without needing a macOS display server.
2. **Swappable Frontends:** If you start with a quick prototype UI in `iced` or `egui` and decide a year later to rewrite the visual interface in `gpui` or native Swift/AppKit via FFI, 80% of the codebase (`core`, `dsp`, `graph`, `engine`, `host`, `project`) remains completely untouched.
3. **Real-Time Sanitization:** You can attach custom global allocators or tools like `assert_no_alloc` specifically inside `daw-engine`'s test suite to mathematically guarantee no future feature accidentally introduces a heap allocation on the audio thread.
